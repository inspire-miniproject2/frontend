# MinwonON 디자인 시스템

> 대상: KRDS React 기반 반응형 공공 민원 웹앱
> 기준 자료: `FRONTEND_STRUCTURE.md`, `MinwonON_Wireframe.pdf` 12개 화면
> 문서 상태: MVP 구현 기준

## 1. 목적과 적용 우선순위

이 문서는 MinwonON의 공통 시각 언어, 레이아웃, KRDS 컴포넌트 사용법, 화면 패턴, 반응형·접근성·상태 표현 규칙을 정의한다. 화면마다 새 스타일을 만들지 않고 이 문서의 토큰과 공통 래퍼를 재사용한다.

자료가 충돌하면 다음 순서를 따른다.

1. API 필드·권한·상태 전이: `api-spec_MinwonON.md`
2. MVP 기능과 확정사항: `FRONTEND_STRUCTURE.md`
3. 정보 구조와 화면 흐름: `MinwonON_Wireframe.pdf`
4. 컴포넌트·토큰·상호작용: 최신 KRDS 가이드와 프로젝트에 고정된 `krds-react` 버전

와이어프레임의 배치와 정보 계층은 참고하되 아래 항목은 구현하지 않는다.

- 보완 대기·보완 필요
- 답변 마감기한, 기한 임박·초과, 처리 예정일
- 카카오톡 알림
- 임시 저장·자동 저장
- 공무원 답변 첨부 등록
- 알림 모두 읽음
- 자동 Access Token 재발급 UI

공개 답변에서는 민원 제목·분야·신청일만 공개하고 민원 본문은 표시하거나 클라이언트 상태에 저장하지 않는다.

## 2. 디자인 원칙

### 2.1 공공성

- 공식 전자정부 배너, 운영기관 식별자, 헤더, 주 메뉴, 브레드크럼, 페이지 제목, 푸터를 일관되게 제공한다.
- 실제 한국어 레이블과 예시 데이터를 사용한다.
- 장식보다 정보 구조, 현재 상태, 다음 행동을 명확히 한다.

### 2.2 절제된 시각 표현

- 흰색과 회색조를 기본으로 하고 KRDS 파란색을 주요 행동과 현재 상태에 제한적으로 사용한다.
- 그라데이션, 글래스모피즘, 과도한 라운드·그림자·장식은 사용하지 않는다.
- 카드 남용을 피하고 제목, 구분선, 여백으로 정보 그룹을 구분한다.
- 상태는 색상만으로 구분하지 않고 텍스트, 아이콘 또는 단계 설명을 병행한다.

### 2.3 예측 가능한 상호작용

- 같은 행동에는 같은 레이블과 버튼 위계를 사용한다.
- 제출·답변 확정처럼 되돌리기 어려운 작업은 영향 안내와 최종 확인을 제공한다.
- 로딩·빈 결과·오류·비활성·완료 상태에서도 사용자가 다음 행동을 알 수 있어야 한다.

## 3. 기술 적용 규칙

- 기본 UI는 `krds-react` 컴포넌트를 우선 사용한다.
- KRDS React 스타일은 앱 진입점에서 한 번만 불러온다.
- 프로젝트 보완 컴포넌트는 `src/shared/ui/krds/`에 래퍼로 작성한다.
- `krds-react` 패키지 내부 CSS나 소스는 직접 수정하지 않는다.
- KRDS가 제공하지 않는 패턴은 KRDS 토큰과 접근성 마크업을 사용해 래퍼로 보완한다.
- 색상·간격·글자 크기·테두리를 화면 CSS에 직접 반복하지 않고 프로젝트 의미 토큰을 사용한다.
- KRDS 버전 변경 시 시각 회귀, 키보드 동작, 컴포넌트 API를 먼저 검증한다.

권장 스타일 계층은 다음과 같다.

```text
krds-react 기본 스타일
  -> 프로젝트 의미 토큰
    -> 공통 KRDS 래퍼
      -> 레이아웃·화면 조합
```

## 4. 토큰

실제 값은 설치된 KRDS CSS 변수를 우선 연결한다. 아래 이름은 앱 코드에서 사용하는 의미 기반 별칭이며, 임의 색상 팔레트를 새로 만들기 위한 값이 아니다.

### 4.1 색상

| 의미 토큰 | 용도 |
|---|---|
| `--minwon-color-surface` | 기본 페이지·입력 배경 |
| `--minwon-color-surface-subtle` | 표 행, 보조 영역, 비활성 배경 |
| `--minwon-color-surface-information` | 개인정보 안내, 자동 배정 안내 |
| `--minwon-color-text` | 본문과 제목 |
| `--minwon-color-text-subtle` | 도움말, 메타데이터 |
| `--minwon-color-border` | 입력, 표, 카드, 구분선 |
| `--minwon-color-primary` | 주요 버튼, 링크, 현재 단계 |
| `--minwon-color-primary-strong` | 강조 링크, 선택 상태 |
| `--minwon-color-danger` | 검증 오류와 실패 |
| `--minwon-color-warning` | 주의·부분 성공·충돌 |
| `--minwon-color-success` | 완료·성공 |
| `--minwon-color-focus` | 키보드 포커스 링 |

사용 규칙:

- 본문 대비는 WCAG AA 이상을 확보한다.
- 링크는 색상뿐 아니라 밑줄 또는 명확한 링크 문맥으로 식별한다.
- 파란색 채움은 한 화면의 핵심 CTA와 현재 선택 상태에 집중한다.
- 성공·경고·오류 색상에는 반드시 상태 텍스트를 함께 표시한다.
- 로고의 태극 색상은 브랜드 식별자 안에서만 사용하며 UI 의미 색으로 재사용하지 않는다.

### 4.2 타이포그래피

- 기본 글꼴: Pretendard GOV를 우선하고 시스템 sans-serif를 대체 글꼴로 둔다.
- 본문 기본 크기: `16px`, 줄 높이 `1.5` 이상.
- 작은 메타데이터는 `14px` 미만으로 축소하지 않는다.
- 긴 민원 본문과 공식 답변은 읽기 폭을 제한하고 문단 간격을 유지한다.

| 역할 | 권장 크기/굵기 | 사용 위치 |
|---|---|---|
| Display | 40/700 | 로그인 등 단일 목적 화면의 핵심 제목 |
| H1 | 36/700 | 페이지 제목 |
| H2 | 24/700 | 주요 섹션 제목 |
| H3 | 20/700 | 카드·패널 제목 |
| Body L | 18/400 | 중요 설명과 결과 요약 |
| Body M | 16/400 | 기본 본문·폼·표 |
| Label | 16/600 | 입력 레이블·열 제목 |
| Caption | 14/400 | 도움말·날짜·메타데이터 |

1024px에서도 제목 계층은 유지하되 H1은 공간에 맞춰 한 단계 축소할 수 있다. 의미상 제목 레벨은 시각 크기와 독립적으로 `h1`부터 순차적으로 사용한다.

### 4.3 간격과 크기

기본 간격 단위는 4px이며 다음 단계만 사용한다.

```text
4, 8, 12, 16, 20, 24, 32, 40, 48, 64, 80
```

- 입력 요소 사이: 20~24px
- 레이블과 입력: 8px
- 연관된 버튼 사이: 8~12px
- 섹션 사이: 40~64px
- 페이지 제목과 첫 콘텐츠: 32~40px
- 최소 클릭·터치 목표: 44x44px
- 입력 및 기본 버튼 높이: 48~56px
- 테두리 반경: KRDS 기본값을 사용하고 임의의 큰 pill 형태는 상태 배지 외에는 피한다.
- 그림자: 알림 팝오버, 모달처럼 레이어 구분이 필요한 경우에만 KRDS elevation을 사용한다.

## 5. 전역 레이아웃

### 5.1 앱 셸

```text
SkipLink
OfficialGovernmentBanner
SiteHeader
  AgencyIdentifier / MinwonON
  GlobalNavigation
  AuthActions 또는 UserMenu
  NotificationCenterTrigger
Breadcrumb
Main
SiteFooter
GlobalDialogLayer
GlobalToastLayer
```

- 콘텐츠 최대 폭은 `1200px`, 1440px 화면에서 중앙 정렬한다.
- 전역 셸과 본문은 같은 좌우 기준선에 맞춘다.
- 브레드크럼 아래에 H1과 한 줄 설명을 배치한다.
- 로그인처럼 좁은 과업은 본문 폭을 약 480~560px로 제한한다.
- 폼·목록·상세는 1200px 콘텐츠 영역을 사용한다.
- 푸터는 콘텐츠가 짧아도 화면 하단의 안정적인 위치를 유지하되 본문을 가리지 않는다.

### 5.2 반응형 기준

| 범위 | 레이아웃 규칙 |
|---|---|
| 1200px 이상 | 최대 폭 1200px, 다열 폼과 상세 2열 허용 |
| 1024~1199px | 좌우 여백 축소, 필터 줄바꿈, 공무원 작업 패널 폭 축소 |
| 1024px 미만 | 전역 메뉴 패널화, 상세 2열을 1열로 전환, 표는 구조화 목록 또는 명시적 스크롤 영역 |

1024px에서는 다음을 반드시 보장한다.

- 주요 CTA와 페이지 제목이 겹치지 않는다.
- 필터는 2열 또는 여러 줄로 재배치되고 검색 버튼이 화면 밖으로 밀리지 않는다.
- 공무원 처리 작업은 본문 다음 순서로 이동 가능해야 한다.
- 차트는 리플로우하며 동일 데이터를 표로 확인할 수 있다.
- 200% 확대에서도 핵심 과업을 가로 스크롤 없이 완료할 수 있다. 데이터 표의 제한적 가로 스크롤은 예외로 하되 키보드 접근과 안내 문구를 제공한다.

## 6. 공통 컴포넌트

### 6.1 버튼

| 종류 | 용도 | 예시 |
|---|---|---|
| Primary | 화면의 대표 완료 행동 | 로그인, 민원 제출, 답변 확정 및 알림 발송 |
| Secondary | 대표 행동의 대안 | 이전, 신청서 수정, 새 민원 신청 |
| Tertiary/Text | 낮은 우선순위 이동 | 목록으로, 회원가입 |
| Danger | 삭제·취소 등 파괴적 행동 | MVP에서는 제한적으로 사용 |

- 한 작업 영역에 Primary 버튼은 원칙적으로 하나만 둔다.
- 아이콘 단독 버튼은 알림처럼 관례가 명확한 경우에만 허용하고 접근 가능한 이름을 제공한다.
- 제출 중에는 버튼을 비활성화하고 레이블을 `제출 중`처럼 바꾼다.
- 비활성 버튼 근처에 비활성 이유를 텍스트로 제공한다.
- 취소는 Secondary로 표현하며 위험 색상을 쓰지 않는다.

### 6.2 폼

- 모든 입력은 화면에 보이는 `<label>`을 갖는다.
- 필수는 레이블 뒤 `*`와 `필수` 설명을 함께 제공하고, 선택 필드는 `선택`으로 표시한다.
- placeholder를 레이블로 사용하지 않는다.
- 도움말 -> 입력 -> 오류 순서로 배치하고 `aria-describedby`로 연결한다.
- 오류는 빨간 테두리만 사용하지 않고 구체적 해결 문구를 제공한다.
- 제출 실패 시 페이지 상단에 오류 요약을 두고 각 오류 입력으로 이동할 수 있게 한다.
- 글자 수는 `현재/최대` 형식으로 표시하고 스크린리더에 과도하게 반복 안내하지 않는다.
- 민원 본문은 개인정보·민감정보 입력 주의 문구를 인접 영역에 제공한다.

### 6.3 파일 업로드·다운로드

- 드래그 앤 드롭과 파일 선택 버튼을 함께 제공한다.
- 허용 형식·개수·개별 용량은 서버 정책이 확정된 값만 표시한다.
- 파일마다 파일명, 크기, 업로드 상태, 제거 행동을 제공한다.
- 업로드 오류는 해당 파일에 인접하여 표시한다.
- 다운로드는 API endpoint를 통해 수행하며 진행·실패 상태를 알린다.
- 공무원 답변 등록에는 파일 업로드를 제공하지 않는다.
- 공개 답변에서는 API가 반환한 공개 첨부만 읽기 전용으로 표시한다.

### 6.4 배지와 상태 단계

상태 레이블은 API enum을 다음처럼 표시한다.

| API | 사용자 레이블 |
|---|---|
| `RECEIVED` | 접수됨 |
| `ASSIGNED` | 배정됨 |
| `IN_PROGRESS` | 처리 중 |
| `COMPLETED` | 완료 |

- 배지는 비대화형 텍스트로 사용한다.
- 현재 상태는 배지 텍스트와 상세 설명으로 함께 전달한다.
- 진행 단계는 `완료`, `현재`, `예정`을 시각·텍스트로 모두 구분한다.
- 시민 흐름은 `접수 -> 부서 배정 -> 담당자 지정 -> 처리 중 -> 완료` 표시 모델을 사용할 수 있으나 API 원본 상태와 매핑 규칙을 코드에 명시한다.
- 완료되지 않은 단계를 완료처럼 파란색으로 채우지 않는다.

### 6.5 안내·오류 메시지

| 유형 | 사용 예 |
|---|---|
| Information | 개인정보 안내, 자동 배정 기준 |
| Warning | 제출 후 수정 불가, 세션 종료, 부분 성공 |
| Error | 검증 실패, API 실패, 다운로드 실패 |
| Success | 접수 완료, 답변 등록 완료 |

- 메시지는 상태명, 결과, 사용자가 할 수 있는 다음 행동 순으로 작성한다.
- API 오류에는 필요할 때 재시도와 `requestId`를 제공한다.
- 접수 성공·이메일 실패 같은 부분 성공은 성공과 실패를 분리해서 설명한다.

### 6.6 표·목록·페이지네이션

- 표 위에 결과 수, 적용된 정렬과 필터를 표시한다.
- 열 제목은 `<th scope="col">`, 행 제목은 필요한 경우 `<th scope="row">`를 사용한다.
- 정렬 버튼은 현재 정렬 방향을 텍스트와 `aria-sort`로 제공한다.
- 제목 링크의 클릭 영역을 충분히 확보하되 행 전체를 모호한 클릭 영역으로 만들지 않는다.
- 페이지네이션은 현재 페이지, 전체 페이지, 이전·다음의 비활성 상태를 전달한다.
- 좁은 폭에서는 중요 필드 순서의 구조화 목록으로 전환한다.
- 빈 결과와 검색 결과 없음은 구분한다. 검색 결과 없음에는 `조건 초기화`를 제공한다.

### 6.7 카드·정의 목록

- 접수 완료, 신청 정보, KPI처럼 경계가 필요한 요약에만 사용한다.
- `dl/dt/dd`를 사용해 레이블과 값을 연결한다.
- 카드마다 과도한 그림자를 사용하지 않고 1px 테두리 또는 배경 차이를 사용한다.

### 6.8 알림 센터

- 헤더의 알림 트리거에는 `알림, 읽지 않은 알림 N개` 형식의 접근 가능한 이름을 제공한다.
- 팝오버 제목, 단건 목록, 생성 시각, 읽음 상태, 이동 대상을 표시한다.
- 단건 `읽음 처리`만 제공하고 `모두 읽음`은 제공하지 않는다.
- 팝오버는 Escape로 닫히고 닫힌 뒤 트리거로 포커스가 복귀한다.
- 1024px 미만에서는 전용 `/notifications` 페이지로 자연스럽게 확장한다.

### 6.9 모달·토스트

- 모달은 제출 확정 등 즉시 판단이 필요한 경우에만 사용한다.
- 제목, 영향 설명, 확인·취소 버튼을 제공하고 focus trap을 적용한다.
- 토스트는 보조 피드백으로만 사용하며 중요한 오류·완료 정보는 본문에도 남긴다.
- 자동으로 사라지는 메시지는 읽을 충분한 시간을 보장하고 필요하면 닫기 버튼을 제공한다.

### 6.10 차트

- KRDS 파란색과 회색조로 구성하며 패턴·직접 레이블을 함께 사용한다.
- 범례만으로 값을 해석하게 하지 않는다.
- 차트 제목, 기간, 데이터 갱신 시각, 한 문장 요약을 제공한다.
- 항상 동일 데이터의 접근 가능한 표 보기를 제공한다.
- API 확정사항에 따라 기한 임박·초과 통계는 표시하지 않는다.

## 7. 화면 패턴

### 7.1 로그인

- 폭이 제한된 단일 열 폼을 사용한다.
- 아이디, 비밀번호, 아이디 저장, 로그인 CTA, 회원가입 이동 순으로 배치한다.
- 역할 선택 UI는 제공하지 않는다.
- 인증 실패는 폼 상단 요약과 해당 입력 근처에 표시한다.

### 7.2 회원가입

- 넓은 화면에서는 2열, 1024px 이하에서는 1열 폼을 사용한다.
- 필드 순서는 아이디, 비밀번호, 비밀번호 확인, 이름, 이메일, 휴대전화번호, 이메일 알림 동의로 유지한다.
- 공무원 계정은 행정 절차로 별도 발급된다는 안내를 강조 정보 영역으로 제공한다.

### 7.3 내 민원·공무원 업무함 목록

- 페이지 제목과 대표 CTA, 상태 요약, 검색·필터, 결과 요약, 표/목록, 페이지네이션 순서로 구성한다.
- 상태 요약은 선택 가능한 필터임을 버튼 또는 탭 의미로 명확히 한다.
- 공무원 업무함에는 기한 위험 열과 보완 상태를 표시하지 않는다.
- 시민 목록에는 민원번호, 분야, 제목, 신청일, 상태를 우선 표시한다.
- 공무원 목록에는 민원번호/제목, 분야, 상태, 담당자, 접수일을 우선 표시한다.

### 7.4 민원 작성·최종 확인·접수 완료

- 세 화면에서 동일한 3단계 표시기를 유지한다: `신청서 작성 -> 내용 확인 -> 접수 완료`.
- 작성 화면은 분야, 제목, 본문, 첨부, 이메일 알림 선택 순서로 구성한다.
- 최종 확인은 읽기 전용 요약과 `제출 후 수정할 수 없음` 확인 체크를 제공한다.
- 임시 저장, 자동 저장, 카카오톡 문구는 표시하지 않는다.
- 접수 완료는 접수번호, 제목, 일시, 분야, 자동 배정 결과, 현재 상태, 알림 채널과 다음 행동을 제공한다.
- 알림 실패가 있어도 접수 성공 여부와 혼합하지 않고 부분 성공 메시지로 분리한다.

### 7.5 민원 상세

- H1 아래에 민원번호와 현재 상태를 함께 표시한다.
- 상태 단계 -> 신청 정보와 본문 -> 첨부 -> 처리 이력 -> 공식 답변 순으로 구성한다.
- 넓은 화면에서는 정보와 본문을 2열로 둘 수 있고 1024px 이하에서는 1열로 전환한다.
- 처리 이력은 시각 타임라인과 날짜·행동 텍스트를 함께 제공한다.

### 7.6 공개 답변 목록·상세

- 목록 상단에 `민원 본문은 공개하지 않는다`는 개인정보 안내를 제공한다.
- 검색은 제목 또는 답변 내용 기준이며 분야·답변 부서·완료 기간 필터를 제공할 수 있다.
- 목록 항목은 분야, 민원 제목, 답변 부서, 완료일, `답변 완료` 상태로 구성한다.
- 상세는 민원 제목·분야·신청일과 공식 답변 전문을 분리한다.
- 민원 본문은 DOM, Query 캐시용 표시 모델, 분석 이벤트에 포함하지 않는다.
- 개인정보 신고 UI는 제공하지 않는다.

### 7.7 공무원 민원 처리

- 넓은 화면은 왼쪽 민원 정보, 오른쪽 처리 작업의 2열 구조를 사용한다.
- 오른쪽 패널은 배정 부서, 담당자, 허용된 상태 전이, 공식 답변, 공개 여부, 확정 CTA 순서로 구성한다.
- 1024px 이하에서는 처리 작업을 본문 아래로 이동하고 하단 고정 패널로 본문을 가리지 않는다.
- 답변 첨부 업로드는 제공하지 않는다.
- 완료 전에는 답변 본문과 공개 여부를 검증하고 잘못된 상태 전이를 차단한다.

### 7.8 관리자 민원처리 현황

- 필터 -> KPI -> 상태별 현황 -> 기간 추이 -> 부서별 표 순서로 구성한다.
- KPI는 전체 접수, 처리 완료, 완료율, 평균 처리일을 사용한다.
- 기한 임박·초과 KPI와 위험 목록은 제거한다.
- 각 KPI에는 단위와 기준 기간을 표시한다.
- 차트마다 수치 요약과 데이터 표 보기를 제공한다.
- 데이터 갱신 시각을 페이지 설명 근처에 표시한다.

## 8. 공통 상태 패턴

| 상태 | 시각·콘텐츠 규칙 | 기본 행동 |
|---|---|---|
| Loading | 레이아웃을 유지하는 스켈레톤 + 로딩 텍스트 | 중복 조작 차단 |
| Empty | 데이터가 없는 이유와 시작 행동 | 민원 신청 등 CTA |
| No Result | 검색 결과 없음과 적용 조건 표시 | 조건 초기화 |
| Validation Error | 오류 요약 + 필드 인접 오류 | 첫 오류로 포커스 |
| API Error | 이해 가능한 메시지 + requestId | 재시도 또는 안전한 이동 |
| Forbidden | 권한 없음 설명 | 역할별 시작 화면 이동 |
| Disabled | 비활성 외형 + 이유 설명 | 조건 충족 방법 안내 |
| Submitting | 진행 상태 텍스트 + 버튼 비활성 | 중복 제출 방지 |
| Success | 결과 요약 | 다음 주요 행동 제공 |
| Partial Success | 성공 결과와 실패 결과 분리 | 실패 항목 재시도 안내 |
| Conflict | 최신 상태와 충돌 원인 설명 | 데이터 다시 불러오기 |

스켈레톤은 실제 콘텐츠와 비슷한 크기로 만들어 레이아웃 이동을 줄인다. 오류 발생 시 입력값을 가능한 범위에서 유지하되 민원 본문과 첨부를 브라우저 영속 저장소에 저장하지 않는다.

## 9. 접근성 기준

- 본문 바로가기 링크를 문서 첫 포커스 요소로 둔다.
- 전역 구조는 `header`, `nav`, `main`, `footer` 랜드마크를 사용한다.
- 페이지당 H1은 하나를 원칙으로 하고 제목 수준을 건너뛰지 않는다.
- 키보드 포커스 링을 제거하지 않으며 배경과 충분한 대비를 확보한다.
- DOM 순서와 시각 순서를 일치시킨다.
- 동적 상태는 필요한 경우 `aria-live`로 알리되 반복 알림을 피한다.
- 상태, 필수 여부, 오류, 차트 범례를 색상만으로 전달하지 않는다.
- 아이콘에는 장식용 여부를 구분하고 대화형 아이콘에는 접근 가능한 이름을 제공한다.
- 모달·팝오버는 Escape, 초기 포커스, focus trap, 트리거 복귀를 지원한다.
- 표의 제목·헤더·정렬·페이지네이션을 스크린리더가 이해할 수 있게 한다.
- 1024px 및 200% 확대, 키보드 전용, Windows 고대비 모드에서 핵심 흐름을 확인한다.

## 10. 콘텐츠 작성 규칙

- 버튼은 명사보다 행동을 사용한다: `민원 제출`, `내용 확인`, `답변 확정 및 알림 발송`.
- 상태는 일관된 한국어 레이블을 사용한다: `접수됨`, `배정됨`, `처리 중`, `완료`.
- 오류는 원인과 해결법을 함께 쓴다: `민원 내용을 20자 이상 입력해 주세요.`
- 날짜는 목록에서 `2026.08.14`, 상세에서 `2026.08.14 14:42`처럼 문맥에 맞춰 일관되게 쓴다.
- 민원번호는 `CIV-2026-000184` 형식을 유지한다.
- 기관명, 부서명, 담당자 이름은 API 값을 사용하고 임의 축약하지 않는다.
- 사용자에게 내부 enum, HTTP 상태, 스택 추적을 노출하지 않는다.

## 11. 구현 구조

권장 공통 래퍼 예시는 다음과 같다.

```text
src/shared/ui/krds/
├─ AppShell
├─ PageHeader
├─ FormField
├─ FormErrorSummary
├─ StatusBadge
├─ StatusStepper
├─ FeedbackBanner
├─ DataTable
├─ Pagination
├─ FileUpload
├─ EmptyState
├─ ErrorState
├─ ConfirmDialog
└─ ChartWithDataTable
```

각 래퍼는 다음 원칙을 따른다.

- KRDS 원본 props를 무분별하게 재노출하지 않고 프로젝트에서 허용하는 변형만 제공한다.
- 텍스트, 상태, 접근성 이름은 호출 측에서 명시한다.
- 기본·hover·focus·active·disabled·loading·error 상태를 Storybook에 문서화한다.
- 컴포넌트 내부에 업무 API 호출을 넣지 않는다.
- 화면별 CSS보다 레이아웃 primitive와 의미 토큰을 우선한다.

## 12. 검수 체크리스트

### 디자인 시스템

- [ ] `krds-react`와 KRDS 스타일 버전이 고정되어 있다.
- [ ] 공식 배너·기관 식별자·헤더·메뉴·브레드크럼·페이지 제목·푸터가 공통 셸로 구현되었다.
- [ ] 화면 CSS에 임의 색상과 반복된 매직 넘버가 남아 있지 않다.
- [ ] 대표 CTA가 화면별로 명확하고 Primary 버튼이 남용되지 않았다.

### 반응형

- [ ] 1440px과 1024px에서 동일한 정보 우선순위가 유지된다.
- [ ] 필터, 표, 공무원 작업 패널, 차트가 잘리거나 겹치지 않는다.
- [ ] 1024px 미만의 구조화 목록 또는 스크롤 대체가 구현되었다.
- [ ] 200% 확대에서 핵심 과업을 완료할 수 있다.

### 상태와 접근성

- [ ] 모든 데이터 화면에 loading·empty·no-result·error 상태가 있다.
- [ ] 제출 화면에 validation·disabled·submitting·success·partial-success·conflict 상태가 있다.
- [ ] 상태를 색상 없이도 구분할 수 있다.
- [ ] 키보드 포커스, 모달·팝오버 포커스 관리, 오류 요약이 동작한다.
- [ ] 차트에 직접 수치·요약·표 대체 보기가 있다.

### 확정사항

- [ ] 보완, 기한, 카카오톡, 임시 저장, 답변 첨부 등록, 알림 모두 읽음 UI가 없다.
- [ ] 공개 답변 화면과 표시 모델에 민원 본문이 없다.
- [ ] 관리자 화면에 기한 임박·초과 KPI가 없다.
- [ ] 공무원 답변 등록은 `responseContent`, `isPublic`만 입력받는다.
